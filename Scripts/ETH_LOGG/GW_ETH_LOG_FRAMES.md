# GW_ETH_LOG Trace Frame Naming

This file documents the software-level names used by `GW_ETH_LOG.pyw`.
The logger receives UDP/TCP payloads from the AURIX gateway and maps the raw
payload format to names that are useful in the trace view.

## Transport

- Default AURIX source IP: `192.168.1.10`
- Default receive ports: `30600, 30490, 30500, 35000, 35001, 54088`
- The logger receiver can listen on multiple ports. Use comma-separated ports
  such as `30600,30490,30500`, or ranges such as `30600-30610`.
- The AURIX source IP filter is applied to every configured receiver port.
- In the trace, `Src Port` is the sender's UDP/TCP source port from AURIX.
  `Rx Port` is the local logger/listener port that received the packet.
- Broadcast destinations seen in Wireshark, such as `192.168.1.255` and
  `255.255.255.255`, are network destinations. They are not the software frame
  names.

## ZGW Payloads

ZGW software frames start with the ASCII magic bytes `5A 47 57` (`ZGW`).
The fourth byte is the ZGW frame type.

| Raw type | Trace name | Meaning |
| --- | --- | --- |
| `0x01` with bus `CANFD` | `CANFDData` | Gateway summary payload carrying decoded CAN FD signal values from the ZGW application. |
| `0x01` with bus `LIN` | `LINData` | Gateway summary payload carrying decoded LIN signal values from the ZGW application. |
| `0x02` | `CommandSignal` | Command signal frame generated by the ZGW command path. |
| `0x03` | `CommandBlock` | Command block frame generated by the ZGW command path. |
| `0x04` | `DTCTransition` | Diagnostic trouble-code transition frame. |
| `0x05` | `AiModel` | AI model result frame with global inference timing and per-channel prediction data. |
| `0x06` | `CpuPerf` | CPU performance counter snapshot frame carrying paged cycle, instruction, timing, sample, overflow, and byte counters. |

The old generic name `Gateway summary` is intentionally not used in the trace
because it describes the container format, not the software data being traced.
When a configured CAN, CAN FD, or LIN range has no readable COM signal values,
the firmware still emits one header-only summary for that bus in the publish
cycle. The logger shows those packets as `signals=0`, which makes disconnected
or silent buses visible instead of making their Ethernet summary packet vanish.

## Non-ZGW Payloads

Payloads that do not start with `ZGW` are treated as known network-management
status traffic when they match the observed 5-byte format.

| Trace name | Observed payload | Meaning |
| --- | --- | --- |
| `Networkmanagement3_Status` | `4E 4D 01 02 00` | Network-management status payload observed from the AURIX UDP stream. |
| `AURIXHeartbeatAck` | ASCII `AURIXHeartbeatAck` | UDP port `30600` response emitted by `SoAd.c` after receiving the logger's `PCHeartbeat` payload. |
| `TimeSync` | Starts with `5A 54 53 31` (`ZTS1`) | Time sync broadcast from `EthTimeSync.c` on UDP port `35000`. The logger decodes sequence, vehicle time ns, UTC time ns, UTC valid flag, time source, sync status, and CRC. |
| `MCUData` | Starts with `5A 4D 43 55` (`ZMCU`) | MCU/status payload from `GatewaySwc.c` on UDP port `35001`. The logger decodes sequence, vehicle time ns, init/wakeup flags, reset code fields, voltage values, temperature values, and CRC. |

Decoded `TimeSync`, `MCUData`, `AiModel`, and `CpuPerf` fields are also exposed as graph signals.
For example, `TimeSync.VehicleTimeNs`, `TimeSync.UtcTimeSeconds`,
`MCUData.TempCore`, `MCUData.Vext`, and `CpuPerf.LastCycles` can be selected
individually from the signal graph drop-down. The graph supports multiple
added signals at the same time. Use `Add` to plot the currently selected drop-down signal, `Remove` to
remove it from the plot, and `Clear` to remove all plotted signals. The graph
uses a rolling time window in seconds and draws square markers at sampled
points. The default graph view is `Stacked`, which gives each plotted signal
its own lane so large values such as time counters do not hide smaller voltage
or temperature signals. `Shared axis` keeps the older common Y-axis behavior.
Use `Zoom +`, `Zoom -`, or the mouse wheel over the graph to change the rolling
time window. Hover near a square sample marker to show the nearest signal name,
time, and value.

If future firmware adds more non-ZGW payloads, add the mapping here first and
then update `decode_gateway_payload()` in `GW_ETH_LOG.pyw`.

## Transmit Rows

Rows produced by the local transmit generator are configured in the
`Transmit generator` table.

- Use `Add packet` to append another packet definition.
- Use `Update selected` to replace the selected row with the current editor
  fields.
- Use `Remove selected` to delete the selected packet definition.
- Double-click a row to toggle it between enabled and disabled.
- The trace `Frame` column uses the configured packet `Name`, for example
  `PCHeartbeat`, `TimeSyncRequest`, or any project-specific name you enter.

`Count = 0` means continuous transmit. Positive `Count` values send that many
packets. When transmit is enabled, the logger starts one sender for each
enabled row in the table.
Multiple enabled transmit rows are started with a small deterministic phase
offset so packets with the same interval do not always hit the AURIX in the
same burst. In `Fixed` trace mode, `Delta ms` is the period since the same
fixed trace row was last updated. Replies received by a transmit socket include
`reply-to=...; rtt=... ms` in the `Info` column so heartbeat and SOME/IP-SD
response timing can be compared directly.

`Use SD Subscribe` fills the editor with a SOME/IP-SD SubscribeEventgroup
packet for ZGW service `0x1234`, instance `0x0001`, eventgroup `0x0001`, TTL
`3 s`. Add that packet and leave it enabled at the default `1 s` interval to
act as the PC subscriber supervised by ZGW_APP.
