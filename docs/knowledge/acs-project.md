# ACS (AURIX Configuration Studio) project

Paths relative to repository root. Evidence: ACS 1.0.24 headless import/build and a TASKING 1.1r8 dry run; source/tool level only, no bench or vehicle validation.

## Why ADS projects do not open in ACS

`ZGW/ZGW_APP` and `ZGW/ZGW_FBL` are ADS (AURIX Development Studio 1.10.40) projects: nature `com.infineon.aurix.buildsystem.aurixnature`, builders `com.infineon.aurix.buildsystem.builders.*`, TASKING toolchain. ACS 1.0.24 lacks the `com.infineon.aurix.buildsystem.*` and `com.tasking.managedbuilder` plugins (it ships only TriCore GCC, SDCC, ARC-LLVM), so it cannot load them. ADS stays installed in `C:\Infineon\AURIX-Studio-1.10.40` and remains the reference environment for the original projects. The firmware targets TASKING; the project built for ACS therefore does not use GCC (a GCC attempt failed on TASKING-only code in `SMU.c`, `McuSm.c`, `port_core{0,1,2}.c` and was removed).

## `ZGW/ZGW_APP_ACS`

CDT makefile project (no managed build) that ACS imports; its builder runs ACS's `tools/make.exe` on `Makefile`, which calls the TASKING tools (`cctc`, `astc`, `elfsize`) directly.

- Sources are **linked** from `../ZGW_APP` (`APP`, `BSW`, `Configurations`, `Libraries`, `Cpu*_Main.c`, `Compiler.h`, `Std_Types.h`, LSL files). Nothing is copied; edit in `ZGW_APP`. The makefile reads `../ZGW_APP` directly and uses `ZGW_APP/Lcf_Tasking_Tricore_Tc.lsl`.
- `tasking_sources.mk` / `tasking_includes.opt` are generated by `ZGW_APP_ACS/tools/gen_tasking_manifest.py` from the ADS "TriCore Debug (TASKING)" `subdir.mk` files: 371 sources, each with the exact cctc/astc option variant ADS used (4 cctc variants, 2 astc variants, e.g. `--tradeoff=4`, `-Og -Os`), and 130 include paths. Re-run after the ADS source set or per-file options change.
- Link step, LSL, hex output, UCB range filter (`Scripts/Build/filter_ihex_ranges.ps1`, range `0xAF400000-0xAF405FFF`) and `elfsize` mirror `ZGW_APP/TriCore Debug (TASKING)/makefile` and `makefile.targets`. Output goes to `ZGW_APP_ACS/Build/TASKING_Debug/` (git-ignored).
- `TASKING_CTC` (default: the ADS-bundled `Tasking_1.1r8/ctc`) selects the toolset.
- Not reproduced: ADS "dependents" step that builds the SCR (SDCC) sub-project (`ZGW_APP/SCR_AURIX_TC3x.c` is compiled as a normal source; rebuild SCR in ADS if it changes), `ZGW_FBL`, Release config, flash/debug launch, iLLD library manager state (`.ads`).

## Known blocker: TASKING license

The ADS-bundled non-commercial TASKING toolset refuses to run outside the ADS IDE: `ctc F104: protection error: License does not support running as standalone. Please use the integrated development environment.` Consequences: the ACS project imports, `make` runs, and the dry run (`make -n`) shows the correct per-file commands, but compilation fails at the first `cctc` call. A real ACS-driven TASKING build needs a TASKING license that allows standalone/command-line use (set `TASKING_CTC` to it). Do not work around the license check. No TASKING object or link output has been produced from this project, so equivalence with the ADS image is unverified.

## Headless check

ACS's `.ini` forces `-showlocation`, which the CDT headless builder rejects. Call the bundled JRE directly: `java -jar plugins/org.eclipse.equinox.launcher_*.jar -application org.eclipse.cdt.managedbuilder.core.headlessbuild -data <ws> -import file:/D:/.../ZGW_APP_ACS -build ZGW_APP_ACS` from `ACS/eclipse`. Import path must be a `file:/` URI.

## Verified TASKING build via ADS headless (scratch copy)

TASKING runs when invoked by the ADS Java process, so the licensed way to build from the command line is ADS's CDT headless builder, not the ACS makefile. Recipe (verified 2026-11-22): copy `ZGW/ZGW_APP` (or `ZGW_FBL`) without its `TriCore Debug (TASKING)` folder plus `Scripts/Build` into a scratch tree with the same relative layout (`<root>/ZGW/ZGW_APP`, `<root>/Scripts/Build`), remove the `...builders.booster` and `...builders.autodiscovery` `buildCommand` entries from the copy's `.project` (they need the GUI workbench and abort headless runs), then from `C:\Infineon\AURIX-Studio-1.10.40` run the bundled JRE with `-jar plugins/org.eclipse.equinox.launcher_*.jar -nosplash -application org.eclipse.cdt.managedbuilder.core.headlessbuild -data <ws> -no-indexer -import file:/<root>/ZGW/ZGW_APP -build "ZGW_APP/TriCore Debug \(TASKING\)"`. The in-repo project and its tracked build outputs were not touched.

**Caveat for `ZGW_APP`: the Project Booster builder changes the image.** It excludes unused iLLD sources from the link; the tracked build did not link `Libraries/iLLD/TC3xx/Tricore/Asclin/Asc/IfxAsclin_Asc.c`, `_Lib/DataHandling/Ifx_CircularBuffer.c`, `Ifx_CircularBuffer.asm.c` and `Ifx_Fifo.c`. With the booster removed these four are linked (360 vs 356 objects) and the hex differs. To reproduce the tracked image, delete those four files in the scratch copy before building. `ZGW_FBL` is not affected.

Results with that recipe:
- `ZGW_FBL`: 0 errors, ~13 s, ROM 0x413b0, RAM 0x2d39b; `ZGW_FBL.hex` and `ZGW_FBL_edited.hex` byte-identical to the tracked `ZGW_FBL.hex` and `Binary/ZGW_FBL_edited.hex`.
- `ZGW_APP` at commit `5f8057c` (the commit that last updated the tracked hex): 0 errors, ~54 s; `ZGW_APP.hex` and `ZGW_APP_edited.hex` are identical (after newline normalization; the repo stores CRLF/LF differently) to the tracked `ZGW_APP.hex` and `Binary/ZGW_APP_edited.hex` of that commit. So the tracked ZGW_APP image is bit-reproducible with ADS 1.10.40 / TASKING 1.1r8, although it was originally built with ADS 1.10.36.
- `ZGW_APP` at current sources (HEAD `2873618`): 0 errors, ROM 0x5a0fa0, RAM 0x7c753; the hex differs from the tracked `ZGW_APP.hex` in 14,944 of 184,542 lines and from `Binary/ZGW_APP_edited.hex`. Cause: `APP/ParallelFlashSwc/ParallelFlashSwc.c`, `BSW/Com/Can/Can.c`, `CanIf/CanIf.{c,h}`, `CanTp/CanTp.c`, `PduR/PduR.c`, `Diag/Dcm/Dcm.{c,h}` and `Dcm_Cfg.{c,h}` changed in the 2026-10-24 commits after the last image update. The tracked `ZGW_APP.hex` and `Binary/ZGW_APP_edited.hex` are therefore stale relative to current sources.

Not flashed or bench-tested.

**Artifact refresh (2026-11-22):** the tracked `ZGW_APP` outputs were replaced with the current-source (HEAD `2873618`) ADS-headless build described above: `Binary/ZGW_APP.elf`, `Binary/ZGW_APP.map`, `Binary/ZGW_APP_edited.hex`, `ZGW/ZGW_APP/TriCore Debug (TASKING)/ZGW_APP.hex` and `.map`. The ELF's debug info references the scratch build path (the previous ELF referenced another machine's Desktop path). `validate_flash_artifacts.py` passes for the ELF/edited-HEX pair with `--allow-elf-ucb` (the ELF contains UCB PT_LOAD segments, as the previous ELF did, so it fails without that flag); the edited HEX has no UCB data. Not flashed or bench-tested. `ZGW_FBL` artifacts were already identical and were not replaced.

## Debugging (standalone winIDEA)

ACS has no winIDEA/iSYSTEM integration (its own debugger is HighTec's AURIX debugger). `ZGW/ZGW_APP_ACS/winIDEA/` holds a copy of the ADS winIDEA workspace (`ADS.xjrf`, `ADS.xgrf`) with the APP/FBL ELF and HEX paths re-pointed (ELF from `Binary/`, HEX from the ADS build folders) and `open_winidea.ps1`, which opens it with the winIDEA from the ADS install. The ADS-launch-only settings (device TC375TP, IFX_DAS/USB, goto `0x80000000`, stop at `core0_main`) are not in the workspace and must be set in winIDEA. See `ZGW/ZGW_APP_ACS/winIDEA/README.md`. Not tested with hardware; winIDEA was not launched during setup.
